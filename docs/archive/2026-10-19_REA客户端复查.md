## F-01：AES 默认值的旧矛盾已定位到 RPC 覆盖

**已确认的静态行为，高置信度。** `EnvelopedDataEncrypt` 路由到 `0x10031de0`。汇编 `0x100327ba` 先设置算法为 4；若请求有 `algo`，取整数后在 `0x100327e2` / `0x100327e4` 通过 `TEST` / `CMOVLE` 把所有小于等于零的值重置成 4；随后 `0x100327ef` 调用 `NetcaPKIMsgEnvelopedDataSetEncAlgorithm`。

底层 `0x1003b3d0` 的 switch 将 4 映射为 `2.16.840.1.101.3.4.1.2`（AES-128-CBC），6 映射为 `2.16.840.1.101.3.4.1.42`（AES-256-CBC）。因此省略 / 0 / -1 → 4 → AES-128-CBC，解释了旧报告“底层初始化为 6”与成功流量使用 AES-128 的差异。旧初始化观察本身无需推翻，但不能直接用于网页层。

当前 `server/rpc.mjs:75` 附近仅接受 -1 / 0 / 6；省略值成为 NaN，显式 4 也会被拒绝。现有站点已捕获的 -1 / 0 路径可用，更广泛的原厂接口兼容仍有缺口。建议后续支持省略 / 4，并先明确其它负值是否需要兼容；不必扩展 DES 等无关算法。

证据：E-01 `ev_3fc2a44aff0ae17baa4871bc2ce47c5810d868fa94e40e85f9dd6d0e1ed4c82b`；E-02 `ev_809a341887d7e6b00fb84b51fade1090923bd9de614408276d1c964ed257028c`；字段名 bytes：`ev_d863b4ea138cbb1823da637551679985e64eba5842c58744f7e8c1e3fb83cf5b`。与旧 E-007 成功流量一致。

## F-02：清软件密码缓存不等于注销设备

**已确认的静态行为，高置信度。** RPC `ClearPwdCache` → `0x1001ea50` → `NetcaPKICryptoClearPwdCache(0)`。Crypto 的全局分支 `0x100c8e20` 遍历软件缓存，释放时间对象，对密码字符串执行 memset(0)，然后释放字符串、记录并把计数清零；该函数可见路径没有设备注销或认证 APDU 调用。

非零设备句柄分支还会清理设备对象内部的软件字段，但同样不能由此推导硬件退出登录。JSON-RPC `0x1002bd30` 存在“先清该设备缓存，再 ReVerifyUserPwd”的独立组合路径；本次未建立该辅助函数的完整外部入口。

**新增细节：** `SignedDataSign` 还支持请求内 `clearPwdCache: true`，会在进入签名 helper 前调用全局清缓存；这与独立 RPC 同名功能相关，但当前桥未读取该参数。它在显式 certPwd 校验之后、实际 CMS 签名前执行，不能简单解释成“签名后清理”。

当前桥保留独立五分钟 PIN 租约是 macOS 短生命周期助手的适配设计；原厂静态代码并没有证明这个时长。现有设备实测的句柄关闭后 6982 记录仍有独立价值。

证据：E-03 `ev_c42cd9dae3ec071e9f922b211ba1551ab46b0c757c8cc3f3cee2f221d12488e3`；E-04 `ev_ede3a21086da670f4c1276a861e35e8c29a43fc48bf1cdaf217c0316428b7aad`；E-05 `ev_d163543556337373f88391ac82ffd519a09f811f07bcc510af2e69b65179fb3f`，汇编交叉确认 `ev_284139828b78fbb25a57c500a2e7fb80de6bc19bdc8522c4863867562954bf82`。

## F-03：特定 PIN 失败走 status=0 的业务结果，而非普通 RPC 失败

**已确认的静态结构，高置信度；未消耗硬件 PIN 次数验证。** `SignedDataSign` 在提供 certPwd 时调用 `NetcaPKICertVerifyUserPIN`；其返回 -5 或 -81 时进入单独分支，构造 `retrynum`（API 输出，初始值 -1）和 `result`（原生返回码），把内部 RPC 状态设成 0，再返回。

公共序列化器 `0x1000e330` 将内部状态复制到 `responseResult.status`，仅在状态为 0 时写入 `responseEntity`。所以该分支结构是 `responseResult.status: 0` 加 `responseEntity: { retrynum, result }`，不会生成 signValue。不要只看 status 判断签名成功，也不要把 -5 / -81 的具体人类含义猜成已验证事实。

当前桥把签名异常交给通用失败路径，未保留该结构。若未来网页依赖原厂剩余次数提示，这是协议差异；展示的重试次数应来自实际设备结果，不能伪造。

证据：E-05；汇编 `0x1003d1c3`、`0x1003d1d7`、`0x1003d1dc`、`0x1003d21c`；E-06 `ev_0a05d0c27a4dc12227c4343a429d58c8c8f7753e9eebe1d603a87bd26cc37895`。

## F-04：证书列表和信封解密的返回契约更完整

**已确认的静态行为，高置信度。** `GetCertList` → `0x10016cd0` 返回 `deviceCount`、`certCount`、`certInfo` 数组；设备信息可用时附 `deviceType`、`deviceSn`、`deviceRetryNum`。无设备分支只明确设置 deviceCount=0，不保证其余字段存在。证书对象构造器 `0x1001a2e0` 还写入 subject/issuer 分量、有效期、序列号、Thumbprint/Thumbprint256、keyUsage、publicKeyBits 等字段，部分字段依赖底层读取成功。

当前桥 `server/rpc.mjs:408` 固定给出一个签名证书，使用 certList/certs，缺少原厂 certInfo。目标页面现有流程已可用，但不能把这些别名视作完整的原厂枚举协议。

`EnvelopedDataDecrypt` → `0x100313f0` 在 Base64 内存返回路径设置 clearValue、clearEncodeType，并调用 `GetEncAlgorithm` 设置 `algo`，再通过共用 helper 加上完整 `certObject`。当前桥 `server/rpc.mjs:340` 缺少 algo，certObject 只含 certCode。

此外原厂解密先加入名为 `device` 的证书库，失败后加入 `my` 库再解密；汇编与字符串 bytes 共同确认。这是增加证书搜索范围的回退，不能解释为自动重试 PIN，也不能证明当前 USBKey 能解开其它证书的信封。

## F-05：响应版本字段也存在兼容差异

**已确认的静态行为，高置信度。** 公共序列化器初始化 `responseVersion: 1`，复制 requestId，并可回传 requestOrigin / lwsObjectId。当前 success/failure 仅写 `requestVersion`。现有网页不一定读取版本字段，但补齐 responseVersion 是可独立验证的小改动。

序列化器对未知函数使用 status=-8、JSON 解析失败使用 -9，并在特定内部状态 -1000 时附 netcaCryptoCode。当前桥使用自己的 -11000 / -11001 错误域；全面替换错误码前需要按网页真正使用的分支逐项对齐。

requestOrigin 在该序列化器中只是复制字段；这不足以证明原厂 WebSocket 层的 Origin 校验是否存在。本次没有分析 NetcaWebSocketServer.exe 的握手实现，不做该安全结论。

证据：E-06。

## F-06：当前源码与“五分钟租约覆盖业务签名”的文档不一致

**当前源码观察，高置信度；用户可见后果为推断。** `server/rpc.mjs:189` 在请求不含 certPwd 时只调用 requestCertificatePin()；后者只读取普通一分钟缓存，不读取五分钟 authenticatedSessionPin。读取五分钟租约的路径在 EnvelopedDataDecrypt。独立 ClearPwdCache 会清掉一分钟缓存。

所以“登录成功 → ClearPwdCache → 不带 certPwd 的业务签名”即使仍有五分钟租约，源码也会走新密码提示；与 `docs/NETCA_WEBSOCKET_PROTOCOL.md:91` 声称租约覆盖业务签名不一致。这是需要补充场景测试的具体路径，不宣称本次已在网站重现。

同样，签名 helper 抛错时 `server/rpc.mjs:195` 不清 authenticatedSessionPin，公钥自检失败分支也不清；解密失败分支则清两个缓存。与文档“私钥操作失败即清除租约”不一致。建议把失败失效策略统一到所有私钥操作，但不要把该源码缺口夸大成已经发生的授权绕过。

## 处理顺序与剩余问题

1. 优先核对业务签名的租约复用与失败失效，针对登录→清缓存→业务签名增加离线依赖注入测试；补测显式错误 PIN 后旧租约是否清理，避免用实物试错。
2. 补齐低风险契约字段 responseVersion、解密 algo，以及显式 algo=4 / 省略算法兼容；保持现有成功 CMS 字节契约。
3. 需要兼容更多页面时，再补 certInfo 与特定 PIN 失败结果，使用公有证书与设备返回值构造真实字段。
